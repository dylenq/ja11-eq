    public func filterCount() -> Int?     // task 2
    public func preGain() -> Double?      // task 2
    public func band() -> Band?           // task 2

    public static func getRequest(_ command: JA11Command, data: [UInt8] = [], form: FrameForm = .padded) -> [UInt8]

    public static func isGetRequest(_ payload: [UInt8]) -> Bool   // true only for those two forms of the four read requests
    public static func replyFrame(from report: [UInt8]) -> FiioReplyFrame?

    public static func uint16BE(_ high: UInt8, _ low: UInt8) -> Int   // task 2

- `swift build`, `swift test` and `swift run` work from the repo root. Swift Testing is available
  (`import Testing`); a passing run ends with a line like `Test run with 2 tests in 1 suite passed`.
- The built executable is at `"$(swift build --show-bin-path)/ja11-probe"`. That path is not
  `.build/debug` on this toolchain, so always ask for it.
- `swift test --filter` with a filter that matches nothing exits 0 and prints
  `No matching test cases were run`. Checks in this plan therefore look for the summary line.
- A class shaped like the `HIDTransport` described in Task 1 — one serial dispatch queue,
  `@unchecked Sendable`, C callbacks passing `self` through `Unmanaged` — compiles cleanly in
  Swift 6 language mode with `import IOKit` and `import IOKit.hid`. That was a compile check only:
  nothing was opened, sent or read on the dongle while planning, so how the device behaves is
  still unknown until Task 1 runs.
- `kIOReturnNotPermitted` is `0xE00002E2` and `kIOReturnNotPrivileged` is `0xE00002C1`.
- IOHIDManager.h: every `IOHIDManagerRegister…` call has to happen before `IOHIDManagerActivate`.
  IOHIDDevice.h says the same for `IOHIDDeviceRegisterInputReportCallback` when a dispatch queue
  is set — which is why Task 1 registers the input-report callback on the manager.
- IOHIDDevice.h on `IOHIDDeviceSetReport`: for a device with several reports, the report ID is
  passed as the argument and is also the first byte of the buffer.
- The dongle shows up in `ioreg -p IOUSB -w0` as `JadeAudio JA11`.
- In this tool environment `grep` is a shell function that runs a bundled ugrep, not
  `/usr/bin/grep`. Every grep form used in this plan's checks was tried under both and gives the
  same result, on a tree that satisfies the guards and on one that violates them. One form does
  differ and is not used here: quiet together with invert (`-q` with `-v`) exits 1 under the
  bundled grep even when non-matching lines exist. Do not rewrite a check into that form.
- The reference implementation (`devicePEQ/fiioUsbHidHandler.js`, fetched while planning and read
  through a summariser, so a cross-check and not a source of truth) agrees with D-03 and D-05 on
  header bytes, command IDs and reply offsets. It sends its frames unpadded through WebHID. D-03
  makes the frame zero-padded to 20 bytes, the full report length the descriptor declares, the
  primary form, and permits that unpadded frame as the one fallback, used only when the padded
  form goes unanswered. D-03 and D-05 are what this plan implements.

3. `Sources/JA11Kit/Protocol/JA11Commands.swift` (D-02): declare `JA11`, `JA11Command`, `JA11SlotID` and `JA11Limits` with the values in the interfaces block. `JA11Command` has exactly four cases, the read commands 0x15, 0x16, 0x17 and 0x18. 4. `Sources/JA11Kit/Protocol/FiioFrame.swift` (D-03, D-06): declare `FrameForm` with the cases `padded` and `unpadded`. `FiioFrame.getRequest(_:data:form:)` builds `[0xBB, 0x0B, 0x00, 0x00, command.rawValue, UInt8(data.count)] + data + [0x00, 0xEE]`. For `.unpadded` it returns exactly those bytes: 8, or 9 with one data byte. For `.padded`, the default, it pads them on the right with zero bytes to exactly `JA11.payloadLength` (20). These are the only two request forms D-03 permits. `FiioFrame.replyFrame(from:)` looks for the header bytes BB 0B at offset 0 and, if they are not there, at offset 1; it tries no other offset. It returns nil when neither offset matches or when fewer than 7 bytes remain from the header onward; otherwise a `FiioReplyFrame` holding `headerOffset`, `command` (frame byte 4) and `bytes` (from the header to the end of the report). `FiioReplyFrame.slotID()` returns frame byte 6 when `command` equals `JA11Command.presetSlot.rawValue`, otherwise nil. `FiioFrame.isGetRequest(_:)` is true only for a payload that is, byte for byte, one of those two forms: BB 0B 00 00, then the raw value of one of `JA11Command.allCases`, then a length byte of 0 or 1, that many data bytes, 00 EE, and after that either nothing (unpadded) or zero bytes up to a total of exactly 20 (padded). It rejects everything else, including any payload longer than 20 bytes, an unpadded frame with extra bytes after its terminator, a padded frame with a non-zero padding byte, and any other header or command byte. `FiioFrame.hex(_:)` renders bytes as two-digit lowercase hex separated by single spaces. This file builds GET frames only (D-04): no function, constant or comment anywhere under `Sources/` may spell out, as hex literals, the SET header or the chip vendor report IDs listed in PROJECT.md section Context.

5. `Sources/JA11Kit/HID/HIDTransport.swift` (D-07, D-08, D-09, D-10): declare `HIDTransportError`, `ConnectionEvent`, `ReportTransport` and `HIDTransport`. `HIDTransport` wraps one `IOHIDManager` created with `IOHIDManagerCreate(kCFAllocatorDefault, IOOptionBits(kIOHIDOptionsTypeNone))` and kept for the life of the process. Create `events` and `reports` with `AsyncStream.makeStream` in `init`, so anything raised before a consumer starts iterating is buffered.
   - `start()` runs once (later calls do nothing). It sets the matching dictionary with both keys, `kIOHIDVendorIDKey: JA11.vendorID` and `kIOHIDProductIDKey: JA11.productID`, through `IOHIDManagerSetDeviceMatching` — never a nil or one-key dictionary. It then registers three manager-level callbacks, `IOHIDManagerRegisterDeviceMatchingCallback`, `IOHIDManagerRegisterDeviceRemovalCallback` and `IOHIDManagerRegisterInputReportCallback`, each with `Unmanaged.passUnretained(self).toOpaque()` as context because C callbacks cannot capture. Only after all three: `IOHIDManagerSetDispatchQueue(manager, queue)` with a private serial `DispatchQueue`, then `IOHIDManagerActivate(manager)`. Do not schedule the manager on a run loop and do not call `IOHIDManagerOpen`.
   - Matching callback (on the queue): if a device is already held, ignore the new one. Otherwise call `IOHIDDeviceOpen(device, IOOptionBits(kIOHIDOptionsTypeNone))`. The exclusive (seize) open option must not be referenced anywhere under `Sources/` (D-08). On `kIOReturnSuccess` keep the device and yield `.connected`; on any other result yield `.openFailed(HIDTransportError.forOpenResult(result))` and do not keep the device.
   - `forOpenResult(_:)`: `kIOReturnNotPermitted` and `kIOReturnNotPrivileged` give `.accessDenied(code:)`; every other code gives `.openFailed(code:)` (D-10).
   - `description`, with the code shown as `0x` plus eight uppercase hex digits: `.accessDenied` is `macOS refused access to the JA11 (IOKit 0xE00002E2). Enable this program under System Settings → Privacy & Security → Input Monitoring, then run it again. If you started it from a terminal, the entry to enable is that terminal app.`; `.openFailed` is `Could not open the JA11 (IOKit 0x…).`; `.sendFailed` is `Could not send to the JA11 (IOKit 0x…).`; `.notConnected` is `The JA11 is not connected.`; `.refusedFrame` is `Refused to send a frame that is not a JA11 GET request.` Only `.accessDenied` mentions Input Monitoring.
   - Removal callback: when the removed device is the held one, drop it and yield `.disconnected`. The manager and its callbacks stay registered, so the next plug-in arrives through the same matching callback with no object recreated (D-09).
